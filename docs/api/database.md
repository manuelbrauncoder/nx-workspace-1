# Database

The API uses PostgreSQL through Drizzle ORM. Table definitions are TypeScript, migrations are plain SQL files generated from them.

## Tables

| Table         | Defined in                                                         | Content                                            |
| ------------- | ------------------------------------------------------------------ | -------------------------------------------------- |
| `users`       | [`auth/users.table.ts`](../src/features/auth/users.table.ts)       | Email (unique), optional name, password hash, role |
| `session`     | [`auth/sessions.table.ts`](../src/features/auth/sessions.table.ts) | Login sessions, managed by the session store       |
| `notes`       | [`notes/notes.table.ts`](../src/features/notes/notes.table.ts)     | Title and sanitized description, belongs to a user |
| `note_images` | [`notes/notes.table.ts`](../src/features/notes/notes.table.ts)     | File name, width and height, belongs to a note     |

- All primary keys are UUIDs generated by the database, except `session.sid`.
- Deleting a user deletes their notes, and deleting a note deletes its image rows (`ON DELETE CASCADE`).
- The `session` table has the layout that the `connect-pg-simple` session store expects. Application code only deletes from it, to revoke a user's sessions.

## Where table definitions live

Each feature defines its tables in a file ending in `.table.ts`. Drizzle picks up all files matching `src/features/**/*.table.ts` (see [`drizzle.config.ts`](../drizzle.config.ts)), so there is no central schema file to keep in sync.

## Changing the schema

1. Edit or add a `*.table.ts` file.
2. Generate the migration:

   ```bash
   pnpm db:generate
   ```

   This compares the table files with the last migration and writes a new SQL file to `drizzle/`. Read it before continuing; it is what will run against production.

3. Apply it locally:

   ```bash
   pnpm db:migrate
   ```

4. Commit the table file and the generated files in `drizzle/` together.

Never edit a migration that has already been applied somewhere. Create a new one instead.

## Migrations in production

The Docker image contains the `drizzle/` folder and the compiled script `dist/scripts/migrate.js`. The production stack runs it in a separate one-off container before the API starts (see [Deployment](deployment.md)). The script only needs `DATABASE_URL`, not the JSON config file.

Drizzle records applied migrations in its own table, so running the script again is safe: it only applies what is new.

## Querying

Services import `db` from [`src/db/index.ts`](../src/db/index.ts) and the tables they need:

```ts
const [note] = await db
  .select()
  .from(notes)
  .where(and(eq(notes.id, noteId), eq(notes.userId, userId)));
```

To look at the local database directly:

```bash
docker compose exec postgres psql -U app -d app
```
