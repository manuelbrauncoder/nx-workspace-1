# Internationalization

The app is translated at runtime. German and English are built in, the user switches the language in the header without a reload, and the server renders the page in the right language straight away.

The translation library is [Transloco](https://jsverse.gitbook.io/transloco). It stays behind [packages/shared/core/src/i18n/](../packages/shared/core/src/i18n/): features, `shared` and the app shell use `I18nService`, the pipe `t` and the pipe `localDate`, nothing else. ESLint enforces that, importing `@jsverse/*` anywhere else fails with "Use I18nService and the pipes from @core/i18n instead." (`I18N_LIBRARY` in [eslint.config.mjs](../eslint.config.mjs)).

## Scopes

Translations are split into scopes, one JSON file per language and scope.

| Scope                | Files                                               | Loaded                          | Keys                |
| -------------------- | --------------------------------------------------- | ------------------------------- | ------------------- |
| Shared texts, ui lib | `packages/shared/ui/src/i18n/de.json`, `en.json`    | Before the first render         | `common.cancel`     |
| Shared texts, app    | `apps/angular-base/src/app/i18n/de.json`, `en.json` | Before the first render         | `layout.nav.notes`  |
| Page scope           | `<page>/i18n/de.json`, `en.json` next to the page   | Lazily, together with the route | `notesList.heading` |

What goes where:

- **Page scope**: the texts of one page and of the components only that page uses. `note-card` is only used by the list, so its texts live in `notesList`
- **Shared texts of the ui lib**: what the wrappers, form controls and toggles need in every app. `common` (cancel, close, retry), `failure`, `form`, `language`, `theme`
- **Shared texts of the app**: everything else used across pages of this app. `layout`, `notFound`, `seo` and the texts of components several pages of a feature use
- A component used by several pages of one feature puts its texts into the shared texts of the app below the name of the feature, e.g. `notes.delete.heading` for `note-delete-button`
- A layout component on the parent route of a feature counts as a page. `showcase-shell` has its own scope on that route

Both kinds of shared texts are merged into the language, so their top-level keys must not overlap. Each source registers its keys in `I18nSharedTexts` and is handed to `provideI18n()`:

[packages/shared/ui/src/i18n/ui.i18n.ts](../packages/shared/ui/src/i18n/ui.i18n.ts)

```ts
declare module '@core/i18n/translation-key' {
  interface I18nSharedTexts {
    common: (typeof de)['common'];
    // ...
  }
}

export const uiI18n = defineI18nSharedTexts<typeof de>({
  de: () => import('./de.json'),
  en: () => import('./en.json'),
});
```

```ts
provideI18n({ shared: [uiI18n, appI18n] });
```

`core` registers `seo` itself (in [seo.service.ts](../packages/shared/core/src/seo/seo.service.ts)), since `SeoService` reads `seo.defaultDescription` and `seo.imageAlt`. Every app provides these two texts in its own shared texts.

Only the active language is loaded. Every file is a hashed lazy chunk, loaded through `import()`, so the server and the browser load it the same way and no HTTP request or cache rule is involved.

### Adding a page scope

`notes` is the reference. A page gets three files and one line in the routes.

[apps/angular-base/src/app/features/notes/presentation/notes-list/notes-list.i18n.ts](../apps/angular-base/src/app/features/notes/presentation/notes-list/notes-list.i18n.ts)

```ts
import { defineI18nScope } from '@core/i18n/i18n-scope';
import type de from './i18n/de.json';

declare module '@core/i18n/translation-key' {
  interface I18nScopes {
    notesList: typeof de;
  }
}

/** Texts of this page, loaded together with its route. */
export const notesListI18n = defineI18nScope('notesList', {
  de: () => import('./i18n/de.json'),
  en: () => import('./i18n/en.json'),
});
```

[apps/angular-base/src/app/features/notes/notes.routes.ts](../apps/angular-base/src/app/features/notes/notes.routes.ts)

```ts
{
  path: '',
  pathMatch: 'full',
  // A route title is a translation key, the scope of the page is loaded before it renders.
  title: 'notesList.title',
  canActivate: [loadI18nScope(notesListI18n)],
  loadComponent: () => import('./presentation/notes-list/notes-list').then((m) => m.NotesList),
},
```

- The `declare module` block registers the scope and its keys. `core` must not import features, so the page tells `core` about its keys instead
- `defineI18nScope` only accepts a registered name, and every language file has to match the shape of the registered German file. A key missing in `en.json` is a compile error
- `loadI18nScope` is a route guard. It waits for the file, so neither the server nor the browser renders a page without its texts
- The route `title` is a key. `SeoService` translates it and updates the page title when the language changes, see [SEO](seo.md)

### Keys are typed

`TranslationKey` is the union of all registered shared texts and of every registered page scope. `I18nService.translate()` and the pipe `t` only accept that type, so a typo fails the build, in TypeScript and in templates:

```text
TS2345: Argument of type '"notesList.headng"' is not assignable to parameter of type 'TranslationKey'.
```

The types know every registered scope, not which one is loaded on the current page. Using a key of another page compiles, but shows the key itself and logs `Missing translation for "..."` through `AppLog`.

## Using translations

### In a template

Import `TranslatePipe` and use the pipe `t`. Values for `{{ placeholders }}` are the argument:

[apps/angular-base/src/app/features/notes/presentation/note-card/note-card.html](../apps/angular-base/src/app/features/notes/presentation/note-card/note-card.html)

```html
<a
  [routerLink]="[note().id, 'edit']"
  [attr.aria-label]="'notes.editNamed' | t: { title: note().title }"
  appUiButton
  variant="outline"
  size="sm"
>
  {{ 'notes.edit' | t }}
</a>
```

```json
{ "notes": { "edit": "Bearbeiten", "editNamed": "Bearbeiten: {{ title }}" } }
```

There is no hard-coded UI text in templates. Inputs of the wrappers take the translated text: `[label]="'noteEditor.fields.title' | t"`.

### In TypeScript

`I18nService.translate()` returns the text in the active language. For something that happens at one moment, a toast or a confirm dialog, call it right there:

```ts
private readonly _i18n = inject(I18nService);

this._toast.success(this._i18n.translate('notes.deleted'));
```

`translate()` reads signals, so it is reactive wherever signals are: in a `computed`, and in the `message` of a validator when it is passed as a function.

[apps/angular-base/src/app/features/notes/presentation/note-editor/note-editor.ts](../apps/angular-base/src/app/features/notes/presentation/note-editor/note-editor.ts)

```ts
required(path.title, {
  message: () => this._i18n.translate('noteEditor.validation.titleRequired'),
});
```

A text that stays on screen must not be stored as a string, or it keeps the language it was created in. Store the key and translate in the template:

[apps/angular-base/src/app/layout/app-nav-items.ts](../apps/angular-base/src/app/layout/app-nav-items.ts)

```ts
export const APP_NAV_ITEMS: AppNavItem[] = [
  { path: '/notes', labelKey: 'layout.nav.notes' },
  { path: '/showcase', labelKey: 'layout.nav.showcase' },
];
```

```html
{{ item.labelKey | t }}
```

### Dates

Use the pipe `localDate` instead of Angular's `DatePipe`. Angular fixes its locale when the app starts, `localDate` formats with `Intl` in the locale of the active language (`de-DE`, `en-GB`):

```html
<time [attr.datetime]="note().updatedAt.toISOString()">
  {{ note().updatedAt | localDate: 'dateTime' }}
</time>
```

| Format     | `de-DE`             | `en-GB`             |
| ---------- | ------------------- | ------------------- |
| `date`     | `12.01.2026`        | `12/01/2026`        |
| `dateTime` | `12.01.2026, 14:05` | `12/01/2026, 14:05` |

New formats are added to `LOCAL_DATE_FORMATS` in [local-date.ts](../packages/shared/core/src/i18n/local-date.ts). `I18nService.locale()` gives the locale for anything else that goes through `Intl`, e.g. numbers.

## Which language

The chosen language lives in the cookie `lang`, not in the URL.

| Where   | Order                                                          |
| ------- | -------------------------------------------------------------- |
| Server  | Cookie `lang`, then `Accept-Language`, then `DEFAULT_LANGUAGE` |
| Browser | Cookie `lang`, then the `lang` attribute the server rendered   |

The server writes the language it decided on into `<html lang>` and the browser takes it over, so both always render the same language and hydration never sees a mismatch. That is also why it is a cookie and not `localStorage` as for the theme: the server has to know it.

`I18nService.setLanguage()` loads the shared texts and every page scope in use in the new language first, then switches, writes the cookie and updates `<html lang>`. `app-language-toggle` in the header calls it.

`languageInterceptor` sends the active language as `Accept-Language` with every request, so a backend can localize its error messages.

### Adding a language

1. Add it to `APP_LANGUAGES` in [languages.ts](../packages/shared/core/src/i18n/languages.ts) with its label and locale
2. Add the file and its loader to the shared texts of the ui lib ([ui.i18n.ts](../packages/shared/ui/src/i18n/ui.i18n.ts)) and of every app (e.g. [app.i18n.ts](../apps/angular-base/src/app/i18n/app.i18n.ts))
3. Add the file and the loader to every page scope. The compiler lists the scopes that still miss the language

## Tests

Every test has the German shared texts of its project, set through `provideI18nTesting()` in the `src/test-setup.ts` of the project, e.g. [apps/angular-base/src/test-setup.ts](../apps/angular-base/src/test-setup.ts). Specs therefore assert German texts.

| Project        | Shared texts in its tests                                                                                                                     |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `angular-base` | ui lib and app                                                                                                                                |
| `ui`           | ui lib                                                                                                                                        |
| `core`         | its own test texts ([core-test-texts.ts](../packages/shared/core/src/testing/core-test-texts.ts)), since `core` knows neither `ui` nor an app |

A spec in a lib that needs texts of an app brings its own scope, like [nav-menu.spec.ts](../packages/shared/ui/src/ui/nav-menu/nav-menu.spec.ts).

The spec of a page loads the scopes that page renders, as the route guard does in the app:

[apps/angular-base/src/app/features/notes/presentation/notes-list/notes-list.spec.ts](../apps/angular-base/src/app/features/notes/presentation/notes-list/notes-list.spec.ts)

```ts
TestBed.configureTestingModule({ providers: [...] });
await loadI18nScopes(notesListI18n);
fixture = TestBed.createComponent(NotesList);
```

The import of the scope is also what makes its keys known to the test build. A spec that renders a page without loading its scope fails to compile with "is not assignable to parameter of type 'TranslationKey'".

## Not included

Plurals and other ICU message syntax. The current texts do not need it. If a project does, add `@jsverse/transloco-messageformat` in `provideI18nLibrary()` ([provide-i18n.ts](../packages/shared/core/src/i18n/provide-i18n.ts)), the rest stays as it is.

## Rules in short

- No hard-coded UI text. Templates use `| t`, TypeScript uses `I18nService.translate()`
- `@jsverse/*` is imported in `core/i18n` only
- One scope per page, loaded by `loadI18nScope` on its route. Shared texts go into the shared texts of the app, or of the ui lib when every app needs them
- Every key exists in every language file
- Texts that stay on screen are stored as keys, not as translated strings
- Dates through `localDate`, not `DatePipe`
- Log messages stay English and are not translated, see [Logging](logging.md)
